    Pick a paper the machine can actually run

    What we did

    Before searching, we checked the machine: nproc gave 4 CPUs, free -h gave 15 GB of RAM, and nvidia-smi didn't exist, so no GPU. That one fact decided everything else.

    Then we searched recent papers (September and October 2026) with three framings: optimizer tricks on tiny transformers, training-free methods on small LLMs, and grokking or interpretability on synthetic tasks. Several framings find different papers than one query does.

    Read the whole paper and turn it into a claim list

    paper/spectral_grokking_2609.26679.md · docs/replication_plan.html

    What we did

    arxiv.org was blocked by this environment's network policy, so we pulled the paper's HTML through Firecrawl's scraper and saved it as markdown. We read the main text and every appendix, because Appendix G is where the reproducible details live: the split, the network, the optimizer, the grid, the phase rules.

    From that we wrote a numbered claim list before writing any code:

    • C0/C1: four specific runs (Fig. 7), including two numbers printed to the digit: first 90% held-out at update 8,300, and a forgetting run peaking at 0.948 and ending at 0.204.
    • C2/C3: a phase map with four outcomes, and a boundary that follows η = A/λ with A ≈ 1.09e-4.
    • C4: grokking time scales as 1/(ηλ).
    • C5: the network's NTK grows Fourier structure after the training set is fit.
    • C6: Theorem 1, the leftover error has a ridge-regression form.
    Takeaway

    Read appendices first when replicating. Write the claims down with the paper's own numbers next to them, so "success" is defined before you see any results.

    Check yourself: which claims are "hard numbers" and which are "shapes"?
    C0/C1 are hard numbers you can match exactly. C3 has a fitted constant. C2, C4, C5 are shapes or trends. Hard numbers are your calibration: if they don't match, nothing downstream means anything.

    The ideas you need

    concepts

    The task

    (a + b) mod 23 for all 529 pairs. Inputs are two one-hot vectors glued together (46 numbers). A pair is for training if (a − b) mod 23 is in a fixed set of 16 values: 368 train, 161 held out. That split doesn't change if you add the same number to a and b, which keeps the cyclic symmetry clean.

    Training

    MSE between the 23 outputs and a one-hot target, averaged over all 368 × 23 numbers. Full-batch SGD (all examples every step, so no noise). Coupled weight decay means each update is w ← w − η(∇L + λw), which is PyTorch's SGD(weight_decay=λ).

    Homogeneity

    The network has no biases: f(x) = W2ᵀ relu(W1ᵀx). Scale every weight by c and the output scales by c². Differentiating that gives Euler's identity J·θ = 2f. This is what lets weight decay be written in terms of outputs, so the math closes.

    The NTK

    J is the Jacobian of all outputs with respect to all weights. The neural tangent kernel K = J Jᵀ says how a gradient step on one output moves every other output. If K stays fixed, the network acts like a kernel machine ("lazy"). If K changes, it is learning features ("rich").

    The paper's argument in four lines

    1. Weight decay leaves a residual: σ* = −c (K + cI)⁻¹ y (weak NTK directions keep more error)
    2. That residual changes the kernel: dK/dt = −K⁽²⁾σ − 2λ̃K
    3. Along one Fourier direction, the strength Λ grows to a stable fixed point Λ* > 0
    4. The slow clock is τ = η·λ·steps → grokking time ∝ 1/(ηλ)
    Takeaway

    You only need three tools to follow the theory: the residual, the NTK, and homogeneity. The long version is in docs/teaching_guide.html.

    Check yourself: why must the network have no biases?
    A bias doesn't scale with the other weights, so f(cθ) = c²f(θ) breaks, and so does Jθ = 2f. Without that identity, the weight-decay term can't be rewritten in output space.

    Build the data and the model

    src/grok/data.py · src/grok/model.py

    The split, in five lines

    def difference_split(p: int = 23, diffs=PAPER_DIFFS_23) -> ModAddData:
    a, b = torch.meshgrid(torch.arange(p), torch.arange(p), indexing="ij")
    a, b = a.reshape(-1), b.reshape(-1)
    diffs = torch.tensor(sorted(diffs))
    train = torch.isin((a - b) % p, diffs)
    return ModAddData(p, a, b, (a + b) % p, train)

    The model

    make_mlp builds a bias-free 46 → 256 → 23 ReLU network with He-normal init after torch.manual_seed(seed). init_weights builds the same network and returns its weights as plain tensors, so every trainer starts from bit-identical weights. That is how the batched trainer could also hit 8,300.

    We also built the mod-97 split from Appendix G.1: the 4,753 unordered pairs, shuffled by NumPy seed 0, first 2,376 for training.

    Takeaway

    When two pieces of code must agree, make them share one source of truth (here, one init function), not two copies that are "the same".

    Check yourself: 46·256 + 256·23 = ?
    11,776 + 5,888 = 17,664 parameters. A test checks this number.

    Two trainers that check each other

    src/grok/train.py

    What we did

    train_reference is the plain PyTorch loop: nn.Module, autograd, torch.optim.SGD. It is slow but obviously right.

    train_batched trains many (η, λ) settings at once with hand-written gradients. The trick: inputs are one-hot, so the first layer is just a lookup, h = W1[a] + W1[23 + b], and its gradient is a scatter-add.

    pre = W1[:, a_tr] + W1[:, b_tr]  # [G, n, width]
h = torch.relu(pre)
dF = (h @ W2 - Y) * scale  # [G, n, p]
gW2 = h.transpose(1, 2) @ dF  # [G, width, p]
dpre = (dF @ W2.transpose(1, 2)) * (pre > 0)
gW1 = torch.zeros_like(W1)
gW1.index_add_(1, a_tr, dpre)
gW1.index_add_(1, b_tr, dpre)
# PyTorch SGD with coupled decay: w <- w - lr * (g + wd * w)
W1.sub_(lrs * (gW1 + wds * W1))
W2.sub_(lrs * (gW2 + wds * W2))

    scale = 2/(n·p) is the derivative of the mean squared error. Tests check both trainers produce the same curves, and that a run's result doesn't depend on which other settings share its batch.

    Takeaway

    When you write a faster version of something, keep the slow obvious version and test one against the other. Every later result rests on that test.

    Check yourself: why does (pre > 0) appear in the backward pass?
    It is the derivative of ReLU: gradient flows only through units that were active. That 0/1 mask is also the source of the "kinks" that matter in lesson 14.

    Test the math the theory depends on

    tests/test_core.py · tests/test_ntk.py · 18 tests

    What the tests guard

    • Data: 368/161 split, labels are (a+b) mod 23, split unchanged by shifting both numbers.
    • Model: no biases, 17,664 parameters.
    • Homogeneity: f(cθ) = c²f(θ) for c = 0.5, 1.7, 3.0, and the Euler identity Jθ = 2f, in float64.
    • Trainers: batched equals reference at three settings; batched runs independent; deterministic.
    • Analysis: phase rules on hand-made curves; a synthetic η = A/λ boundary is recovered.
    • NTK: closed-form kernels equal autograd's J Jᵀ; metric sanity cases (lesson 13).
    _, j_theta = jvp(f, (params,), (params,))   # J·θ without building J
torch.testing.assert_close(j_theta, 2 * base)
    .venv/bin/python -m pytest -q
    Takeaway

    Test the properties the theory assumes, not only the code paths. If homogeneity silently broke (say someone adds a bias), every later conclusion would be invalid, and this test catches it.

    Check yourself: what does jvp(f, (params,), (params,)) compute?
    A Jacobian-vector product: the derivative of f in the direction θ itself, which is J·θ. It never builds the full Jacobian, so it's cheap.

    Make the sweep fast and crash-proof

    src/grok/sweep.py

    Measure before optimizing

    We assumed batching many networks per process would be fastest. Benchmarks said otherwise: one model on one thread took 21 s; 32 models on 4 threads cost about 37 core-seconds each. The matrices (368 × 256 × 23) are too small to use multiple threads well. So: one single-threaded process per core, 3 workers, one core left free for other work.

    Use the paper's exact grid

    The paper's grid is 84 learning rates (0.1 to 100) × 90 weight decays (5e-6 to 2e-3), log-spaced. We took every second point: 42 × 45 = 1,890 runs. Each of our cells sits exactly on one of theirs, so any cell can be compared directly.

    Crash-proofing

    tmp = path.with_suffix(".tmp.npz")
np.savez_compressed(tmp, lr_idx=lr_idx, wd_idx=wd_idx, ...)
os.replace(tmp, path)   # atomic: a file is either complete or absent

    Runs are grouped into 270 chunks of 7. A finished chunk is a file; on restart, existing files are skipped. A crash loses at most one chunk, never a half-written file.

    What went wrong: denormal numbers

    The sweep took 355 minutes, not the ~3.5 hours planned. The slow chunks were all at very large learning rates. There the network "dies" (every ReLU switches off), so the only force left is weight decay, shrinking every weight by (1 − ηλ) each step. Around step 10,000 the weights drop below 1.2e-38, into denormal floating-point range, which CPUs process very slowly: the last 4,000-step segments ran at half speed in a plain loop, and those chunks took ~800 s instead of ~150 s. One line at the top of each worker, torch.set_flush_denormal(True), would have avoided it.

    PYTHONPATH=src .venv/bin/python -m grok.sweep --out results/mlp23 --stride 2 --workers 3
    Takeaway

    Long jobs must be resumable and must write atomically. The cloud container can be reclaimed at any time.

    Check yourself: why write to a temp file and then rename?
    A rename is atomic on the same filesystem. If the process dies mid-write, only the .tmp file is broken, and the resume logic never mistakes a partial file for a finished chunk.

    The phase map and the 1/λ boundary

    src/grok/analysis.py · figures/fig3a_phase_map.png

    Labeling each run

    def classify(train_acc, test_acc, thr=0.9):
    if tr[-1] > thr and te[-1] > thr: return GROK
    if tr[-1] > thr:                  return MEMORIZE
    if (tr > thr).any():              return FORGET
    return NOFIT

    Finding and fitting the boundary

    For each weight-decay column, the boundary is the geometric midpoint between the last "memorized" learning rate and the first "grokked" one. Then we fit η = A/λ with the slope fixed at −1 (log A is just the mean of log η + log λ), plus a free-slope fit as a diagnostic.

    QuantityPaperOurs
    A in η = A/λ1.092e-41.057e-4 (3% off)
    Fit quality, log-RMSE0.1200.110
    Free log-log slope−1.17−1.13
    Highest λ that still groks≈ 7.0e-47.29e-4
    Forgetting starts at λ≈ 8.38e-48.34e-4
    Instability edge (low λ)η ≈ 18.9η ≈ 20.6

    Outcome counts: 472 grokking, 798 memorization, 116 forgetting, 504 no fitting. We even see the paper's "detached high-learning-rate island" around η ≈ 30 to 50.

    What went wrong

    My first "fit fails at λ = …" metric printed 5e-6, the smallest decay on the grid. It counted unstable high-η runs as fit failures. Redefined as "lowest λ where forgetting appears", it gave 8.34e-4 against the paper's 8.38e-4.

    Takeaway

    When a metric returns the edge of your grid, suspect the metric before the science.

    Check yourself: why a geometric midpoint, not an arithmetic one?
    The grid is log-spaced, so the natural midpoint is the midpoint in log space: √(η₁·η₂).

    The timing law: when more data changed the answer

    figures/fig3b_timing_law.png

    What happened

    Halfway through the sweep (the low-decay half), grokking time vs 1/(ηλ) had a log-log slope of 0.96, R² 0.94. It looked like a clean win. With all 1,890 runs, pooling every grokking run gave 0.59, R² 0.59.

    How we diagnosed it

    If the law holds, log₁₀(η·λ·s₁₀) is constant. So we tabulated that quantity by region instead of trusting one fit:

    RegionDeviation from the medianWhy
    λ ≤ 2e-4, η 1 to 16within ±0.12 dexbulk: the law holds
    λ 4e-4 to 8e-4+0.48 dex (~3× slower)next to the mode cutoff; the theory predicts critical slowing there
    η > 16+0.20 dexnext to the instability edge
    fastest runsfloor ~700 to 1,000 updatescan't generalize before fitting the training set

    In the bulk (244 runs): slope 0.94 at the 10% crossing, 1.00 at 50%, 1.02 at 80%, all R² ≈ 0.96.

    Be honest about this

    I chose the "bulk" region after seeing the pooled result. Its edges come from the paper itself (its weak-decay fit range and its stability edge), but it is still a post-hoc choice, and the report says so next to both numbers.

    Takeaway

    Partial data can flatter you. One summary number can hide distinct regimes; break the data down by region before concluding. Report both the pooled and the restricted result.

    Check yourself: why does the 10% crossing give a lower slope (0.94) than the 50% one (1.00)?
    The 10% crossing sits closer to the fitting stage, which costs a roughly fixed number of steps. That offset flattens the curve. Later thresholds are dominated by the slow clock, so they follow 1/(ηλ) more cleanly.

    Seeds, and why η and λ aren't equal partners

    scripts/seed_check.py · results/seeds/

    The paper sweeps one random seed. We took three grokking cells and trained 5 seeds each.

    ChangePredicted speed-upMeasured (5 seeds)
    η × 1.691.69×1.66× to 1.68×
    λ × 2.032.03×1.42× to 1.53×

    An explanation from the paper's own slow-time definition τ = ηλ(s − s_fit): the fit stage costs about α/η updates no matter what λ is. So s₁₀ ≈ α/η + C/(ηλ). Changing η scales both terms; changing λ scales only the second. Fitted on two cells, this predicted the third cell to within 2.2% for every seed.

    What went wrong

    The same offset model fitted across the whole sweep was useless (R² 0.04, with a negative intercept on the half-grid). It works locally, near those cells, not globally. We kept that in the report instead of only showing the local win.

    Takeaway

    A model that predicts well in one neighborhood can fail across the whole space. Test locally, then globally, and report both.

    Check yourself: what is a "held-out cell prediction" here?
    We fitted α and C using two cells, then predicted the third cell's crossing before looking at it. Predicting data you didn't fit on is much stronger evidence than fitting all three.

    Looking inside the network, and two metric bugs

    src/grok/ntk.py · scripts/ntk_mod97.py · figures/fig2_ntk_fourier.png

    The closed-form kernel

    For our one-hidden-layer net the NTK has an exact formula, tested against autograd:

    ⟨∇f_c(x), ∇f_d(x′)⟩ = [c = d]·⟨h, h′⟩ + (x·x′)·Σₖ W2[k,c]·W2[k,d]·mₖ·m′ₖ

    We tracked the "true-label" kernel on mod 97, averaged it by label into a 97 × 97 matrix, and normalized its diagonal to 1, as in Appendix G.1. Modular structure should make that matrix circulant: each entry depends only on (c − c′) mod 97.

    Bug 1: the metric said 1.000 at initialization

    "Circulant share" was 1.000 for a random network. A matrix with 1s on the diagonal and a near-constant value elsewhere is trivially circulant, so the metric was measuring the normalization. Fix: score only off-diagonal variation, and add a test that "identity plus a constant" scores 0. Corrected: 0.01 at init, 0.73 by update 6,000.

    Bug 2: the "task strength" tracked the diagonal

    To get an unnormalized strength (closer to the paper's Λ), I took the largest non-constant eigenvalue of the circulant part. It was 1.01 at init, again the diagonal, which adds the same amount to every frequency. Fix: strongest frequency minus the median frequency, which cancels that constant exactly.

    Corrected result: the k = 1 Fourier mode's strength went 0.016 (update 3,000) → 0.026 (training fully fit, ~7,000) → 0.033 (20,000), then flat. It grew 28% after the fit and plateaued, as the theory's stable fixed point predicts. But most of the Fourier shape formed earlier, while training accuracy climbed from 71% to 99.5%. So: partly reproduced.

    Takeaway

    Test every metric on a case where the right answer is zero. Both bugs would have been caught in one minute that way.

    Check yourself: why do the eigenvectors of a circulant matrix look like waves?
    Every circulant matrix is diagonalized by the discrete Fourier transform, so its eigenvectors are sines and cosines over 0..p−1. That's why "Fourier structure" and "circulant" are the same thing here.

    The ridge check, a controlled experiment, and a 6 GB surprise

    scripts/ridge_check.py · scripts/ridge_control.py

    The derivation we tested

    At a stationary point of mean((f − y)²) + (λ/2)|θ|², multiply the stationarity condition by J and use Jθ = 2f:

    σ* = −c (K + cI)⁻¹ y, with c = λ·n·p → σⱼ / yⱼ = −c / (Λⱼ + c)

    The investigation

    1. Grokking cell after 24,000 updates: 25% relative error, correlation 0.50. Diagnostic: |∇objective| / |∇data| = 0.41, so the net is not at a stationary point.
    2. Polishing with L-BFGS: stalled at 0.37. Continuing SGD to 300,000 updates (84 slow-clock units): still 0.45.
    3. Is my check wrong? Controlled experiment: same tiny problem, only the activation changed. Smooth x² (3-homogeneous): gradient ratio fell to 1.4e-6 and the formula matched to 3.2e-7. ReLU: stuck at 0.30, error 0.12.

    Conclusion: the check and the identity are right. ReLU networks under SGD with weight decay don't settle into a smooth stationary point, so for the paper's actual networks the formula is a good approximation (the predicted curve tracks the data across 5 orders of magnitude), not exact.

    The 6 GB surprise

    The process died twice with no Python error. dmesg showed the out-of-memory killer at 13 GB. Cause: torch.einsum("uk,vk,kc,kd->ucvd", ...) built a hidden 368 × 368 × 256 × 23 intermediate (~6.4 GB in float64). Rewritten as one matrix product, peak memory fell from 7.4 GB to 2.9 GB, and the autograd test still passed.

    A = (M[:, None, :] * W2.T[None, :, :]).reshape(n * p, -1)
K = (A @ A.T).view(n, p, n, p)
K *= (X @ X.T)[:, None, :, None]
K += (H @ H.T)[:, None, :, None] * torch.eye(p, dtype=X.dtype)[None, :, None, :]
    .venv/bin/python scripts/ridge_control.py square 0.2 200000
    Takeaway

    When a result disagrees with theory, isolate one variable with a control before blaming either the code or the paper. And when a process vanishes silently, check the kernel log for the OOM killer.

    Check yourself: why is the x² network 3-homogeneous, and what changes in the formula?
    Scaling θ by c scales the hidden activations (W1ᵀx)² by c², then W2 adds one more c: c³. So D = 3 and the constant becomes c = λ·n·p·3/2 instead of λ·n·p.

    Operations: blocked sites, background jobs, losing nothing

    the unglamorous part
    • Blocked hosts. arxiv.org and download.pytorch.org were blocked. Fixes: read the paper through Firecrawl; install PyTorch from PyPI (allowed), which pulled a 5.5 GB CUDA build that still runs fine on CPU.
    • Background jobs. Long runs used nohup … & with logs, plus a waiter that notifies when done.
    • A waiter that never finished. pgrep -f ridge_check.py matched its own command line, so "wait until it exits" waited forever. Fix: ps -C python, which only lists Python processes.
    • A queue that fired early. [ a -nt b ] behaves differently when b doesn't exist yet. Fix: wait on the actual process ID with kill -0 PID.
    • Ephemeral machine. The container can be wiped when idle, so we committed often and pushed to GitHub as soon as the repo existed, including partial sweep chunks.
    Takeaway

    Most lost time in real projects is operational. Make waits explicit, write logs, and push results off the machine regularly.

    Check yourself: why does pgrep -f name match itself?
    -f matches against full command lines, and the shell running the loop has "name" in its own command line. So the pattern is always found.

    How to talk about it, and what to try next

    interview prep · exercises

    Your 30-second version

    "I independently replicated a September 2026 theory paper on grokking from its appendix, because the code wasn't public. I matched its printed numbers exactly, swept 1,890 networks on CPU, and confirmed the phase map and the 1/λ boundary within 3%. The headline timing law holds away from the phase boundaries but bends near them, and two of the theory's finer claims only partly held. I reported both."

    "How did you know your code was right without theirs?"
    Three levels: unit tests for the math the theory uses (homogeneity, Euler identity, closed-form NTK vs autograd), exact matches to numbers printed in the paper, and only then the scientific claims.
    "What's the most interesting thing you found?"
    Learning rate and weight decay don't act symmetrically: the fitting stage costs ~1/η steps regardless of λ. And the ridge formula is exact for smooth networks but only approximate for ReLU, which I showed with a one-variable control experiment.
    "What went wrong?"
    Two metrics measured a normalization artifact (caught by testing on a null case), an einsum blew up memory to 13 GB (fixed with a matmul rewrite), and a promising early result (slope 0.96) didn't survive the full dataset.

    Exercises

    1. Run the probe with double the weight decay (2.36658e-4). Lesson 12 says the crossing moves earlier by about 1.5×, not 2×. Check it.
    2. Add a bias to the first layer and run pytest. Which test fails, and why does that matter for the theory?
    3. Change the phase threshold from 0.9 to 0.8 and rebuild the phase map. Which boundaries move?
